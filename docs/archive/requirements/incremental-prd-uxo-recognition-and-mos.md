## 1. 项目信息

- **项目名称**：UXO_v1 排弹抢修指挥系统
- **技术栈**：Qt 5 / CMake / C++17 桌面客户端，目标程序 `UXOMissionControl`
- **MVP 约束**：仅允许本地模拟、只读分析、接口占位；禁止接真实设备/真实 AI/真实数据库写入（见 `docs/dev/simulation-policy.md`、`AGENTS.md` 安全边界）
- **原始需求复述**：为 UXO_v1 规划两个从零开始的新功能——(1) 最小应急起降带（MOS）规划，跑道受损后自动规划满足紧急起降最小尺寸的可用区域；(2) 未爆弹识别，在 MVP 阶段以模拟识别服务 + 数据结构 + UI 展示 + 人工确认回路的方式落地，为未来真实 AI 接入留好接口边界。

## 2. 产品目标

### 2.1 功能一：最小应急起降带（MOS）规划

> **v2 修订：多方案递进选址与修复规划** —— 由原"单方案最大空矩形 + 2D 可视化"升级为"多方案递进选址与修复规划系统"：基于最大空矩形算法（A线·计算几何），叠加修复程度递增（0→部分→更多）的多方案框架，每档重算起降带并估算修复时间/难度，按对选址影响排序修复优先级，支持循序渐进展示修复进度与选址变化。算法优先实现可用版本，可视化对比 UI 放 P1。

| 编号 | 产品目标 | MVP 阶段定位 |
|------|---------|-------------|
| MOS-G1 | 在受损跑道模型上，用最大空矩形算法自动计算满足飞机紧急起降最小尺寸要求的可用矩形区域（轴对齐），输出坐标、尺寸；并作为多方案递进规划的计算内核 | 模拟数据驱动，本地纯算法计算（栅格扫描近似），不依赖真实传感器 |
| MOS-G2 | 提供"修复程度递增"的多方案递进框架：方案1（不修复）仅基于当前受损状态算最大可用起降带；方案2 修复部分受损点后重算并给出修复时间/难度；方案3 在方案2基础上修复更多点，输出优化后起降带及对应修复时间/难度 | MVP 用模拟修复工程量估算（逻辑模型），每档为"已修复点子集 + MOS 位置 + 修复时间 + 修复难度"的完整方案 |
| MOS-G3 | 按对起降带选址影响大小对受损点排序，优先修复影响最大的位置，支持循序渐进展示修复进度与选址变化；并最终以可视化对比呈现各方案起降带位置的变化趋势 | 算法与数据模型优先（P0），多方案可视化对比 UI 放 P1（用户明确算法优先） |

### 2.2 功能二：未爆弹识别

| 编号 | 产品目标 | MVP 阶段定位 |
|------|---------|-------------|
| UXR-G1 | 建立未爆弹识别结果的完整数据模型，覆盖类型、子型、置信度、当量估算、识别方法和降级链状态 | 扩展现有 `TargetInfo`，纳入 DDR-008 提出的 `YieldEstimate` 结构 |
| UXR-G2 | 提供模拟识别服务，基于演示场景生成可信的识别结果，模拟型号识别→融合→保守降级的分层链 | 纯本地模拟，输出预定义识别结果，不接真实 AI |
| UXR-G3 | 提供人工确认回路：操作员可查看识别详情、确认/驳回/修正识别结果，修正优先级高于自动估计 | 人始终在回路中，符合 DDR-008 降级链的并行通道设计 |

## 4. 需求池

### 4.1 功能一：MOS 规划（v2 修订：多方案递进选址与修复规划）

> 本次修订将 MOS 从"单方案最大空矩形 + 2D 可视化"升级为"多方案递进选址与修复规划系统"。P0 聚焦算法可用版本（最大空矩形 + 多方案递进框架 + 修复优先级 + 修复时间/难度估算逻辑模型），多方案可视化对比 UI 放 P1（用户明确算法优先）。UXR 部分维持 V1.0 不变。

#### P0 — MVP 必须有的最小可用闭环（算法优先）

| 需求编号 | 名称 | 描述 | 验收标准 | SRS 对应 |
|---------|------|------|---------|---------|
| MOS-001 | 跑道与损毁模型 | 定义跑道几何数据结构（长度、宽度、朝向角、坐标系）和损毁点数据结构（位置、类型[弹坑/未爆弹]、影响半径）。弹坑影响半径含可见弹坑半径 + 结构损伤扩展区；未爆弹影响半径 = 殉爆安全距离 D = K × W^(1/3)。损毁点额外携带"是否已修复"状态与修复工程量属性（供递进规划使用）。 | 1) 跑道模型可从 JSON 配置加载；2) 损毁点含坐标(m)、类型、半径(m)、是否已修复、来源标注；3) 数据结构有中文注释标注"模拟数据结构" | 新增（SRS 无） |
| MOS-002 | 最大空矩形算法（A线·计算几何） | 给定跑道矩形和"未修复"损毁点集合，计算满足最小尺寸约束（长度≥L_min, 宽度≥W_min）的最大轴对齐空矩形（A线内核）。约束：MOS 矩形不与任何未修复损毁点影响圆相交；MOS 矩形边与跑道轴线平行（MVP 不支持斜向）。MVP 用栅格扫描近似法（Aggarwal/Suri 精确算法的近似版），后续可迭代优化。 | 1) 输入跑道 3000×500m + 5 个模拟损毁点，输出至少 1 个满足尺寸约束的 MOS 矩形；2) MOS 矩形与所有未修复损毁影响区无交集（几何验证）；3) 无法找到满足约束的 MOS 时返回"无可用区域"并说明原因；4) 算法为纯本地计算，无外部依赖；5) 同一输入结果确定可复现 | 新增（SRS 无） |
| MOS-003 | 多方案递进规划框架 | 系统支持在"修复程度递增"的多个档位上分别调用 MOS-002 计算起降带，形成递进方案集。方案1（档位0·不修复）：基于当前全部受损状态算最大可用起降带；方案2（档位1·修复部分）：将按 MOS-004 排序的前 N 个高影响受损点标记为"已修复"后重算起降带；方案3（档位2·修复更多）：在方案2基础上再修复下一批高影响点后重算。每个方案为完整对象：已修复点列表 + MOS 位置/尺寸 + 累计修复时间 + 累计修复难度。档位数可配置（默认3）。 | 1) 默认输出方案1/2/3 共 3 个递进方案；2) 每个方案含"已修复点列表、MOS 矩形、修复时间、修复难度"；3) 档位越高，已修复点越多、MOS 面积不减小（单调非减）；4) 档位数可通过参数调整（2~5）；5) 所有计算纯本地、确定性 | 新增（SRS 无） |
| MOS-004 | 修复优先级排序 | 根据后续排弹任务规划需求，对受损点按"对起降带选址影响大小"排序：优先修复影响最大的位置。影响度量采用逻辑模型（如：修复后释放的可起降面积增量 / 是否使 MOS 达到最小尺寸 / 离跑道中心轴线距离等，权重可配置）。输出排序后的修复优先级列表，并支持循序渐进展示修复进度与对应选址变化。 | 1) 输出按影响从大到小排序的受损点列表；2) 排序依据可在参数中配置（权重）；3) 排序结果用于驱动 MOS-003 的递进修复顺序；4) 每一档修复后能在结果中体现"已修复到第几优先级" | 新增（SRS 无） |
| MOS-005 | 修复时间/难度估算（逻辑模型） | 为单个损毁点及每个修复档位估算修复工程量：修复时间（小时）与修复难度（Low/Medium/High）。MVP 用简化逻辑模型——按损毁类型（弹坑回填 vs 未爆弹排除）、尺寸/体积、深度、位置等给出估算值，参数可配置。每个方案汇总其档位内所有已修复点的累计修复时间与最大/综合难度。 | 1) 每个损毁点可独立估算修复时间+难度；2) 每个方案汇总累计修复时间（各点之和）与综合难度等级；3) 估算参数可从 JSON 配置（如弹坑回填速率 m³/h、未爆弹排除基准工时）；4) 标注"模拟估算，非真实工程量" | 新增（SRS 无） |
| MOS-006 | MOS 参数配置 | 提供配置界面或配置文件，可设置：目标机型最小起降长度(L_min)、最小宽度(W_min)、殉爆安全系数 K、弹坑结构损伤扩展系数、**递进档位数（默认3，范围2~5）**、修复优先级权重、修复时间/难度估算参数。 | 1) 参数可通过 UI 或 JSON 修改；2) 修改参数后重新规划，结果立即更新；3) 参数有合理默认值（如 L_min=460m, W_min=15m, K=1.5, 档位数=3）；4) 默认值标注为"示例值，待业务确认" | 新增（SRS 无） |
| MOS-007 | 单方案 2D 基础可视化（当前档位） | 在 2D 跑道俯视图上展示当前选中档位的规划结果：跑道轮廓、未修复弹坑区域（红色填充）、未修复未爆弹安全距离区域（黄色填充）、已修复点标记（灰色✓）、当前档位 MOS 区域（绿色半透明矩形+边界标注）。支持鼠标缩放和平移。 | 1) 跑道、损毁区、MOS 区域用不同颜色区分；2) MOS 矩形上标注起止坐标和尺寸；3) 已修复点有区别于未修复点的视觉标记；4) 标题或图例明确标注"模拟规划结果·方案N"；5) 视图可缩放和平移 | 新增（SRS 无） |

## 6. 优先级建议

### 建议开发顺序：先做未爆弹识别（UXR），再做 MOS 规划

| 维度 | 未爆弹识别（UXR） | MOS 规划 |
|------|-------------------|----------|
| **数据依赖** | 无前置依赖，扩展现有 `TargetInfo` 即可 | MOS 的安全距离计算依赖当量估算（UXR-001 的 `YieldEstimate`），先做 UXR 可避免 MOS 用临时假数据 |
| **需求清晰度** | SRS F-020~F-032 有明确需求，DDR-008 有详细可行性分析，数据结构已定义 | SRS 中无对应需求，业务定义（尺寸约束、机型假设、安全系数）待澄清，需先回答待确认问题 |
| **架构影响** | 扩展核心数据模型 `TargetInfo`，是后续所有功能（决策、处置、MOS）的基础 | 依赖扩展后的数据模型，属于上层业务功能 |
| **风险控制** | 低风险——需求和数据结构明确，实现路径清晰 | 中风险——业务定义未确认，算法约束可能随业务澄清而变更 |
| **演示价值** | 高——指挥员可看到每个目标的类型/当量/置信度，是态势感知核心 | 高——直接回答"跑道还能不能起降"的核心使命问题 |

**具体建议**：

1. **第 1-3 周**：完成 UXR P0（15 人天）。扩展 `TargetInfo` + `YieldEstimate`，实现 `MockRecognitionService`，打通识别结果展示和人工确认回路。同时，业务方并行澄清 MOS 的业务定义（见第 7 节待确认问题）。
2. **第 4-8 周**：完成 MOS P0（22 人天，v2 多方案递进）。基于 UXR 产出的 `YieldEstimate` 数据结构，实现跑道损毁模型、最大空矩形算法、多方案递进规划框架、修复优先级排序与修复时间/难度估算逻辑模型、单方案 2D 基础可视化。MOS 多方案可视化对比 UI（P1）视演示反馈安排。
3. **第 7-8 周**：根据演示反馈，挑选 UXR P1 和 MOS P1 中的高价值需求迭代。
