## 1. 直接回答

**可以做到。** 而且不需要发明什么新架构——汽车工业的 HIL（硬件在环）测试和自动驾驶行业的 SIL（软件在环）测试用的就是同一套思路：

> 定义抽象接口 → 仿真和真机各做一个实现 → 通过配置文件切换 → 主程序代码完全不变

你们现有代码其实已经埋了这个伏笔。`DemoScenarioProvider.h` 的注释写的是：

> *"后续接入真实数据源时，应通过接口替换，而非修改本文件。"*

原始设计者已经预见到需要接口替换。我们要做的是把这个思路从"目标/任务/设备的模拟数据"扩展到"视频流和遥测数据"。

**但有一个关键前提**：仿真必须走和真机相同的协议（RTSP 推视频、MQTT 推遥测），而不是在代码里直接读文件。这就是"协议级仿真"。

## 2. 核心设计原则：协议级仿真

### 2.1 两种仿真路线的对比

| 路线 | 怎么做 | 优点 | 缺点 |
|------|--------|------|------|
| **代码级仿真** | 在 C++ 代码里用 `#ifdef SIMULATION` 切换，仿真时直接读本地文件生成 QImage | 简单直接 | 切换时要改代码（或重新编译）；仿真和真机走不同的代码路径，Bug 只在真机时才暴露 |
| **协议级仿真**（推荐） | 仿真环境用 FFmpeg 把视频推到 RTSP 服务器，用 Python 脚本把遥测推到 MQTT Broker；主程序永远走 RTSP+MQTT 拉流 | 主程序代码零改动，切换只改配置文件；仿真和真机走完全相同的代码路径 | 需要额外运行仿真服务进程 |

### 2.2 为什么协议级仿真是关键

```
                   主程序看到的接口
                   ┌─────────────────────────┐
                   │  IVideoSource            │
                   │  open(url) → bool        │
                   │  onFrameReady(QImage)    │
                   │  onError(msg)            │
                   └────────┬────────────────┘
                            │
              ┌─────────────┴──────────────┐
              │                            │
     仿真时：url =                          真机时：url =
     rtsp://localhost:8554/visible          rtsp://192.168.1.100:8554/streaming/live/1
              │                            │
     背后是 FFmpeg 推的                     背后是 DJI 遥控器推的
     本地视频文件                           无人机实时画面
              │                            │
              └──────────┬─────────────────┘
                         │
                   主程序的拉流解码代码
                   完全相同——它不知道也不关心
                   URL 背后是什么
```

**核心洞察**：如果仿真和真机都通过 RTSP 协议推送 H.264 视频，那么主程序的拉流、解码、渲染代码就是同一套代码。切换时，只需要把配置文件里的 URL 从 `rtsp://localhost:8554/visible` 改成 `rtsp://192.168.1.100:8554/streaming/live/1`。

遥测数据同理：仿真 Python 脚本推 MQTT，真机 DJI Cloud API 也推 MQTT。主程序的 MQTT 订阅和 JSON 解析代码完全相同。

## 3. 抽象边界放在哪里

这是整个设计中最关键的决策。放得太高（粗粒度），灵活性不够；放得太低（细粒度），接口太多维护成本高。

### 3.1 推荐的抽象边界

```
抽象三个接口：
  IVideoSource      —— 视频流（可见光/红外/任意通道）
  ITelemetrySource  —— 遥测数据（位置/姿态/电量/状态）
  IDeviceCommand    —— 设备控制指令（下发到无人机/机器人）

不抽象的（直接在主程序里实现）：
  AI 推理管线        —— 无论数据从哪来，推理逻辑一样
  3D 态势呈现        —— 无论位置数据从哪来，渲染逻辑一样
  UI 交互            —— 无论数据源是什么，界面操作一样
```

### 3.2 为什么这样划分

| 接口 | 为什么需要抽象 | 仿真实现 | 真机实现 |
|------|---------------|---------|---------|
| IVideoSource | 视频来源不同（本地文件 vs RTSP 流） | RtspVideoSource 拉 `rtsp://localhost:8554/xxx` | RtspVideoSource 拉 `rtsp://192.168.x.x:8554/xxx` |
| ITelemetrySource | 遥测来源不同（Python 脚本 vs DJI MQTT） | MqttTelemetrySource 订阅 `localhost:1883` | MqttTelemetrySource 订阅 `192.168.x.x:1883` |
| IDeviceCommand | 控制指令去向不同（打印日志 vs 发 MQTT） | LoggingCommandSink（只记录不发） | MqttCommandSink（发到 DJI Cloud API） |

**重要发现**：IVideoSource 和 ITelemetrySource 的仿真实现和真机实现**是同一个类**！因为协议级仿真让它们走相同的代码路径。真正的区别只在配置参数（URL、端口、Topic）。

### 4.2 接口定义

**IVideoSource.h**：

```cpp
#pragma once
#include <QObject>
#include <QImage>
#include <QString>

namespace Core::DataSource {

// 视频流统计信息
struct VideoStats {
    int width = 0;
    int height = 0;
    double fps = 0.0;           // 实际帧率
    int bitrateKbps = 0;        // 码率
    int droppedFrames = 0;      // 丢帧数
    qint64 totalFrames = 0;     // 总帧数
    bool isConnected = false;
};

// 视频流源抽象接口
// 仿真模式：RtspVideoSource 拉 rtsp://localhost:8554/xxx
// 真机模式：RtspVideoSource 拉 rtsp://192.168.x.x:8554/xxx
// 实现类相同，只是 URL 不同
class IVideoSource : public QObject {
    Q_OBJECT
public:
    explicit IVideoSource(QObject* parent = nullptr) : QObject(parent) {}
    virtual ~IVideoSource() = default;

    // 连接到视频源
    virtual void open(const QString& url) = 0;
    // 断开
    virtual void close() = 0;
    // 是否已连接
    virtual bool isConnected() const = 0;
    // 获取统计信息
    virtual VideoStats stats() const = 0;

signals:
    // 新帧到达（UI 渲染用）
    void frameReady(const QImage& frame);
    // 连接状态变化
    void connectionChanged(bool connected);
    // 错误
    void errorOccurred(const QString& message);
    // 统计信息更新（每秒一次）
    void statsUpdated(const VideoStats& stats);
};

} // namespace
```

**ITelemetrySource.h**：

```cpp
#pragma once
#include <QObject>
#include <QString>
#include <QDateTime>

namespace Core::DataSource {

// 遥测数据快照（兼容 DJI Cloud API OSD 格式）
struct TelemetrySnapshot {
    // 位置
    double latitude = 0;
    double longitude = 0;
    double altitude = 0;

    // 姿态
    double heading = 0;     // 航向（度）
    double pitch = 0;       // 俯仰
    double roll = 0;        // 横滚

    // 速度
    double horizontalSpeed = 0;
    double verticalSpeed = 0;

    // 电池
    int batteryPercent = 0;
    double batteryTemp = 0;

    // 其他
    int gpsSatellites = 0;
    QString flightMode;     // AUTO_MISSION / MANUAL / RTH / ...
    QString deviceId;       // 设备序列号

    // 视频流 URL（由遥测数据携带，告诉客户端去哪里拉流）
    QString visibleStreamUrl;
    QString thermalStreamUrl;

    QDateTime timestamp;
};

// 遥测数据源抽象接口
// 仿真模式：MqttTelemetrySource 订阅 localhost:1883
// 真机模式：MqttTelemetrySource 订阅 192.168.x.x:1883
// 实现类相同，只是 Broker 地址和 Topic 不同
class ITelemetrySource : public QObject {
    Q_OBJECT
public:
    explicit ITelemetrySource(QObject* parent = nullptr) : QObject(parent) {}
    virtual ~ITelemetrySource() = default;

    // 连接到遥测源
    virtual void connect(const QString& broker, int port,
                         const QString& topicPrefix) = 0;
    // 断开
    virtual void disconnect() = 0;
    // 是否已连接
    virtual bool isConnected() const = 0;
    // 最新一帧遥测
    virtual TelemetrySnapshot latestSnapshot() const = 0;

signals:
    // 遥测数据更新（约 1Hz）
    void telemetryUpdated(const TelemetrySnapshot& snapshot);
    // 设备上线
    void deviceOnline(const QString& deviceId);
    // 设备离线
    void deviceOffline(const QString& deviceId);
    // 连接状态变化
    void connectionChanged(bool connected);
    // 错误
    void errorOccurred(const QString& message);
};

} // namespace
```

### 4.4 DataSourceManager 工厂

```cpp
// DataSourceManager.cpp 伪代码

bool DataSourceManager::initialize(const QJsonObject& config) {
    QString mode = config["mode"].toString();  // "simulation" 或 "production"

    // 创建视频源（仿真和真机用同一个类，只是 URL 不同）
    auto videoArray = config["video_sources"].toArray();
    for (const auto& v : videoArray) {
        auto obj = v.toObject();
        auto* source = new RtspVideoSource(this);
        source->open(obj["url"].toString());
        m_videoSources[obj["id"].toString()] = source;
        // source 的 frameReady 信号会驱动 UI 更新
    }

    // 创建遥测源（仿真和真机用同一个类，只是 Broker 地址不同）
    auto telemObj = config["telemetry"].toObject();
    m_telemetrySource = new MqttTelemetrySource(this);
    m_telemetrySource->connect(
        telemObj["broker"].toString(),
        telemObj["port"].toInt(),
        telemObj["topic_prefix"].toString()
    );

    // 控制指令（仿真和真机不同）
    if (mode == "simulation") {
        m_commandSink = new LoggingCommandSink(this);  // 只记录不发
    } else {
        m_commandSink = new MqttCommandSink(this);      // 发到 DJI Cloud API
    }

    return true;
}
```

## 5. 哪些能完全解耦，哪些不能

### 5.1 能完全解耦的（切换零代码改动）

| 能力 | 为什么能解耦 |
|------|-------------|
| 视频拉流与解码 | 仿真和真机都是 RTSP + H.264，解码管线完全相同 |
| 遥测数据接收 | 仿真和真机都是 MQTT + JSON，解析逻辑完全相同 |
| AI 目标检测 | 输入是 QImage/cv::Mat，不关心来源 |
| 3D 态势呈现 | 输入是经纬度+姿态，不关心来源 |
| UI 交互 | 按钮点击/面板切换，与数据源无关 |
| 告警处理 | 输入是告警事件，与数据源无关 |
| 视频录制/截图 | 输入是 QImage，与来源无关 |

### 5.2 需要专门设计才能解耦的

| 能力 | 差异 | 如何处理 |
|------|------|---------|
| 断线重连 | 仿真几乎不断线，真机会断 | 接口层实现自动重连 + 指数退避，两种模式共用 |
| 视频花屏 | 仿真不花屏，真机会花屏 | 解码层实现 I帧等待逻辑，两种模式共用 |
| 帧率波动 | 仿真帧率固定，真机有波动 | 渲染层实现自适应帧率，两种模式共用 |
| 数据缺失 | 仿真数据完整，真机可能缺字段 | 解析层做字段校验 + 默认值，两种模式共用 |
| 延迟补偿 | 仿真零延迟，真机 100-400ms | 时间戳对齐逻辑，两种模式共用 |

**关键**：以上这些"真机才会遇到的问题"的容错代码，必须在仿真阶段就写好。因为接口层代码是共用的，写了就两种模式都生效。

### 5.3 无法完全解耦的（切换时需要额外工作）

| 能力 | 为什么不能 | 切换时需要做什么 |
|------|-----------|-----------------|
| **DJI Thermal SDK** | 仿真没有 R-JPEG 文件 | 真机时下载无人机拍摄的红外照片文件，送入 Thermal SDK |
| **媒体文件管理** | 仿真用本地文件，真机从云端下载 | 真机时增加云端文件下载逻辑 |
| **DJI Cloud API 特有功能** | 航线管理、远程解锁等功能 | 真机时额外集成 Cloud API 的这些模块 |
| **多机协同** | 仿真脚本可模拟多机，但行为简单 | 真机时需要处理多台遥控器的网络拓扑 |

这些无法解耦的部分，建议在接口定义中预留扩展点（如 `IMediaProvider` 接口），但仿真阶段先不实现。

## 6. 切换时的实际情况

### 6.1 从仿真切换到真机的步骤

```
步骤 1：停止仿真环境
  $ ./simulation/scripts/stop_simulation.sh

步骤 2：修改配置文件
  编辑 config/system.json 的 data_sources 段：
  - mode: "simulation" → "production"
  - video_sources[].url: localhost → 遥控器实际 IP
  - telemetry.broker: localhost → 服务器实际 IP

步骤 3：启动真机环境
  - 打开无人机和遥控器
  - 在 DJI Pilot 2 中配置 Cloud API 的 MQTT 和 RTSP 地址
  - 启动服务器端的 MQTT Broker 和 RTSP Server

步骤 4：启动主程序
  $ ./build/src/App/UXOMissionControl
  → 主程序读 config/system.json → 创建 RtspVideoSource(真机URL)
  → 连接成功 → 画面出现

代码改动：0 行
```

### 6.2 但实际上会遇到的调整

虽然代码不用改，但**参数调优**是免不了的：

| 需要调的参数 | 仿真时的值 | 真机时可能要调 | 在哪里调 |
|-------------|-----------|--------------|---------|
| RTSP 缓冲大小 | 0ms（零延迟） | 200-500ms（抗抖动） | RtspVideoSource 构造参数 |
| 断线重连间隔 | 5秒 | 10-30秒（避免频繁重连） | RtspVideoSource 配置 |
| MQTT 心跳间隔 | 10秒 | 10-30秒 | MqttTelemetrySource 配置 |
| AI 推理帧率 | 30fps（每帧都推） | 10-15fps（降低 CPU 压力） | AI 管线配置 |
| 视频渲染帧率 | 30fps | 25-30fps（自适应） | VideoStreamPanel 配置 |

这些参数都应该放在配置文件中，不在代码里硬编码。这样切换时改配置就行。

## 7. 与现有代码的关系

### 7.1 现有代码中已经有的"解耦伏笔"

| 现有文件 | 现有状态 | 如何融入新架构 |
|---------|---------|---------------|
| `DemoScenarioProvider.h` | 已有注释"通过接口替换" | 保留不动——它负责目标/任务/设备的模拟数据，和视频/遥测是正交的 |

| `Qt5::Network` | 已链接未使用 | 直接用于 MQTT 客户端 |

**总计**：新增约 1000 行，改造约 65 行。现有代码的 95% 不受影响。

## 8. 风险与边界条件

### 8.1 设计风险

| 风险 | 严重度 | 缓解措施 |
|------|:---:|---------|
| FFmpeg C API 在 Qt 中的线程安全 | 高 | 视频解码放在独立 QThread，通过信号传递 QImage 到 UI 线程 |
| MQTT 客户端库选择 | 中 | 优先用 Qt5::MqttClient（官方）；不可用时用 mosquitto C 库 |
| 仿真视频素材与真机差异大 | 中 | 尽早获取真实无人机航拍素材，替换仿真视频 |
| 配置文件格式膨胀 | 低 | `data_sources` 段保持简洁，复杂参数用独立 JSON 文件 |

### 8.2 仿真环境的局限（诚实评估）

| 仿真能做到 | 仿真做不到 |
|-----------|-----------|
| 验证 RTSP 拉流+解码+渲染管线 | 验证 DJI O4 图传的真实延迟和稳定性 |
| 验证 MQTT 订阅+JSON 解析 | 验证 DJI Cloud API 的真实消息频率和字段完整性 |
| 验证 AI 检测在视频帧上的效果 | 验证真实红外热成像的噪声特性对 AI 精度的影响 |
| 验证 UI 交互和数据流 | 验证多无人机同时推流的网络压力 |
| 验证断线重连逻辑（手动断 RTSP） | 验证真实无线环境下的丢包模式 |
| 验证时间戳对齐逻辑 | 验证遥控器固件版本差异导致的兼容性问题 |

**结论**：仿真能覆盖约 80% 的开发验证工作。剩下的 20% 必须用真机验证——但到那时，你的代码架构已经准备好了，不需要推倒重来。

### 8.3 何时应该开始真机验证

以下条件**满足任意两个**时，就应该考虑买无人机做真机验证：

1. 仿真环境下视频拉流→解码→AI→渲染全管线已跑通且稳定运行 24 小时
2. AI 目标检测模型在仿真视频上的准确率达标
3. 断线重连测试通过（手动断开 RTSP 10 次，每次都能在 5 秒内自动恢复）
4. 即将进行客户演示或阶段评审

## 附录：业界参考

这种"协议级仿真+接口抽象"的模式在以下领域是标准做法：

| 领域 | 叫什么 | 怎么做 |
|------|--------|--------|
| 汽车电子 | HIL（硬件在环） | 真实控制器连接仿真器，仿真器模拟传感器信号 |
| 自动驾驶 | SIL（软件在环） | 仿真平台生成虚拟传感器数据，算法在真实代码中运行 |
| 通信设备 | 测试仪表 | 真实基站连接信道仿真器，仿真器模拟无线信道 |
| 航空航天 | 铁鸟试验台 | 真实飞控软件连接仿真器，仿真器模拟气动环境 |

**共同特点**：被测软件不知道连接的是真实设备还是仿真器——因为接口和协议相同。
