## 1. 执委会摘要

### 1.1 我们在做什么

排弹抢修指挥系统的目标是：无人机在空中盘旋侦查 → 画面传回指挥席 → 软件自动分析图像中的未爆弹药 → 指挥员决策处置。

本报告回答一个问题：**怎么让无人机拍摄的画面可信地、实时地、稳定地传到你的指挥软件中？**

### 1.2 核心结论

| 结论 | 说明 |
|------|------|
| **技术可行** | 基于 DJI 行业无人机 + 标准协议的技术路线是成熟的，已有大量类似系统案例 |
| **关键技术风险可控** | 视频延迟、网络中断、数据同步等问题都有成熟的工程解决方案 |
| **仿真到真机的切换不是"改一行URL"** | 需要做架构上的准备（缓冲策略、断线重连、降级方案），但不需要推倒重来 |
| **推荐分四阶段推进** | 仿真开发(2月) → 链路验证(1月) → 真机联调(1月) → 系统集成(1月) |
| **研发阶段最低硬件投入** | ¥0（纯仿真）~ ¥4,788（消费级无人机做链路验证） |

### 1.3 需要你关注的三个关键决策

1. **视频传输协议选 RTSP 还是 RTMP？**（第5节给出对比分析，推荐 RTSP）
2. **要不要在研发阶段买无人机？（第6节给出分级方案）**
3. **仿真程度到哪里为止？（第6.1节给出仿真能覆盖和不能覆盖的清单）**

## 2. 系统通信架构全景

### 2.1 通俗理解

想象一下你在看电视直播。这个过程是：

```
演播室摄像机 → 编码器(压缩画面) → 卫星/光纤(传输) → 你家电视机(解码显示)
```

无人机的图传本质上是一回事，只是把"卫星/光纤"换成了"无线信号"：

```
无人机相机 → 机载编码器 → 无线信号 → 地面遥控器 → 网络 → 你的指挥软件
```

### 2.2 实际链路（以 DJI 行业无人机为例）

### 2.3 对我们来说，哪些是黑盒、哪些是白盒？

| 环节 | 我们能控制吗？ | 说明 |
|------|:---:|------|
| ① 无人机飞行控制 | ✗ | DJI 封闭系统，飞手通过遥控器操作 |
| ② 机载相机图像采集 | ✗ | DJI 封闭系统 |
| ③ **机载编码（H.264/H.265）** | ✗ | DJI 决定编码参数 |
| ④ **无线图传链路（O4协议）** | ✗ | DJI 私有协议，加密传输 |
| ⑤ 遥控器的"上云API"功能 | ✓ | 配置 MQTT 地址、流媒体地址 |
| ⑥ **遥控器到服务器的网络** | ✓ | WiFi/4G/5G/有线，我们部署 |
| ⑦ **服务器端接收与分发** | ✓ | 我们搭建 MQTT Broker + 流媒体服务器 |
| ⑧ **指挥席客户端接收与处理** | ✓ | 我们开发的 Qt/C++ 软件 |

**关键理解**：我们不是从无人机直接拿数据。我们通过 DJI 遥控器作为"中继网关"，获取视频和遥测。遥控器到服务器这段网络是我们能控制的。

## 3. 链路逐段分析

### 3.1 视频编码——为什么画面会"压缩"？

**通俗理解**：无人机拍的原始画面非常大。4K@30fps 的原始数据大约是 3 Gbps（每秒3亿字节）。4G 网络通常只有 10-50 Mbps。所以必须在飞机上就把画面压缩 100-1000 倍。

**实际参数**（以 DJI Mavic 3T/M4T 为例）：

| 参数 | 可见光通道 | 红外通道 | 说明 |
|------|-----------|---------|------|
| 编码格式 | H.264 或 H.265 | H.264 | H.265 比 H.264 压缩率高约50% |
| 分辨率 | 1080p (1920×1080) | 640×512 或伪彩色1080p | 红外传感器原生分辨率较低 |
| 帧率 | 30fps | 9-30fps | 红外帧率通常低于可见光 |
| 典型码率 | 4-8 Mbps | 1-4 Mbps | 取决于画面复杂度和运动速度 |
| **两路合计** | **5-12 Mbps** | | 同时传输可见光+红外 |

**这意味着什么**：
- 需要一条稳定传输 5-12 Mbps 的双向通道
- 如果网络带宽不够（比如 4G 信号差），画面会自动降质或卡顿
- 编码是有损的——画面到我们手上时已经有轻微的质量损失

### 3.2 无线传输——延迟到底多少？

**通俗理解**：延迟就是"无人机看到画面"到"你屏幕上显示画面"的时间差。如果延迟太高，就像打游戏卡顿——看到的画面是几秒前的，没法做实时决策。

**各段延迟实测数据**：

| 传输段 | 延迟 | 说明 |
|--------|------|------|
| DJI O4 私有图传（空中→遥控器） | **15-30ms** | DJI 官方数据，实测可信 |
| 遥控器内处理 + 协议转换 | **50-100ms** | 从 O4 私有协议转为 RTSP/RTMP |
| 网络传输（WiFi/4G/5G） | **5-50ms** | 局域网极快，4G 约20-50ms |
| 客户端缓冲 + 解码 + 渲染 | **20-50ms** | 取决于播放器的缓冲策略 |

| 协议方案 | 端到端总延迟（实测） | 适合实时决策吗？ |
|----------|---------------------|:---:|
| DJI O4→RTSP(TCP)→客户端 | **150-400ms** | ✅ 可以 |
| DJI O4→RTSP(UDP)→客户端 | **100-300ms** | ✅ 可以，但有丢包风险 |
| DJI O4→RTMP→客户端 | **2-30秒** | ❌ 不适合实时场景 |
| DJI O4→Agora(WebRTC)→客户端 | **200-500ms** | ✅ 可以，需额外 SDK |

**重要发现**：DJI Cloud API 的 **RTMP 直播模式延迟高达 2-30 秒**，完全不适合需要实时决策的排弹场景。**必须使用 RTSP 或 Agora(WebRTC) 模式。**

### 3.3 带宽——够不够用？

**问题**：同时传输一路1080p可见光（~6Mbps）+ 一路红外（~3Mbps）= 约 9 Mbps 的持续带宽需求。

**实际网络环境评估**：

| 网络环境 | 典型可用带宽 | 够用吗？ |
|----------|------------|:---:|
| 本地 WiFi (5GHz) | 100-300 Mbps | ✅ 绰绰有余 |
| 4G LTE (良好信号) | 10-30 Mbps | ✅ 够用，有余量 |
| 4G LTE (弱信号) | 2-5 Mbps | ⚠️ 紧张，可能需要降质 |
| 5G (良好信号) | 100-500 Mbps | ✅ 绰绰有余 |
| 有线局域网 | 100-1000 Mbps | ✅ 绰绰有余 |

**实际场景分析（机场跑道）**：
- 机场跑道长 3000m，宽 50m
- 无人机在跑道上方 100m 盘旋
- 遥控器在地面，无人机到遥控器距离通常 < 2km
- DJI O4 图传在 2km 距离内信号稳定，带宽充足
- **主要瓶颈不在空中链路，在遥控器到指挥服务器的网络**

### 3.4 实际传输中会遇到的问题

| 问题 | 什么情况下发生 | 对我们系统的影响 | 如何处理 |
|------|---------------|-----------------|---------|
| **视频卡顿** | 网络抖动、带宽不足 | 指挥员看到的画面不连贯 | 客户端缓冲 + 自适应码率 |
| **画面花屏（马赛克）** | 关键帧(I帧)丢失 | 画面出现绿色块/马赛克 | 等下一个I帧到达自动恢复 |
| **画面黑屏** | 严重丢包或连接断开 | 丢失监控视野 | 断线重连 + 显示"信号丢失"提示 |
| **延迟累积** | 客户端处理跟不上推流速度 | 看到的画面越来越滞后 | 智能追帧算法（丢弃过时帧） |
| **两路画面不同步** | 可见光和红外走不同协议 | 同一时刻两路画面不一致 | 时间戳对齐 |
| **MQTT 消息丢失** | 网络不通畅 | 状态栏数据不更新 | QoS + 心跳检测 + 重连 |

## 4. 仿真与真实环境的差距

### 4.1 差距全景

这是上一份报告中最大的一处草率——我说"改一行 URL 就能从仿真切到真机"。这句话从概念上没错，但省略了大量工程细节。以下是真实差距。

| 维度 | 仿真环境 | 真实环境 | 差距有多大 |
|------|---------|---------|:---:|
| **视频源** | 本地预录 MP4 文件 | 无线信号传输的实时流 | 天壤之别 |
| **延迟** | 0ms | 100ms-30s (取决于协议) | 巨大 |
| **画面质量** | 原始质量，无损失 | 经过 H.264 压缩，有编码损失 | 中等 |
| **丢包率** | 0% | 0.1%-5% (取决于信号) | 中等 |
| **连接稳定性** | 永远在线 | 可能随时断连 | 巨大 |
| **帧率** | 固定30fps | 可能波动（25-30fps） | 小 |
| **视频格式** | 任意容器格式 | 固定的 H.264/H.265 TS 流 | 中等 |
| **分辨率** | 任意 | 1080p 或 720p | 小 |
| **遥测数据** | 完美的每秒1条 | 可能有 1-3 秒的间隔波动 | 小 |
| **多路同步** | 手动对齐的文件 | 两路自然同步（同一时钟源） | 小 |

### 4.2 仿真能验证什么，不能验证什么

| 能充分验证 | 仿真阶段需要专门设计才能验证 | 仿真阶段基本无法验证 |
|-----------|---------------------------|---------------------|
| ✅ AI 目标检测模型效果 | ⚠️ 网络中断时的重连恢复 | ❌ 真实图传的画质损失对 AI 精度的影响 |
| ✅ UI 交互逻辑 | ⚠️ 高延迟下的操作体验 | ❌ 无线干扰导致的瞬时丢帧 |
| ✅ MQTT 数据解析 | ⚠️ 视频花屏时的画面处理 | ❌ 真实红外热成像的噪声特征 |
| ✅ 3D 态势叠加 | ⚠️ 流媒体服务器性能压力 | ❌ 遥控器固件版本的兼容性问题 |
| ✅ 视频解码管线 | ⚠️ 多路流的内存/CPU 占用 | ❌ 真实部署环境的网络拓扑 |

### 4.3 如何弥补这个差距

**关键原则：仿真阶段就要为真实环境写代码，而不是先写"够用就行"再重构。**

具体做法：

1. **在仿真阶段就要实现缓冲和丢帧处理逻辑**——不要等真机联调时才发现
2. **用各种"坏的"视频素材测试**——人为降低画质、插入丢帧、降低帧率
3. **模拟网络中断**——定期断开 RTSP 连接，验证重连+恢复逻辑
4. **用 FFmpeg 模拟真实延迟**——推送视频流时加 `-itsoffset` 参数模拟延迟

```bash
# 模拟高延迟环境下的视频流
ffmpeg -re -stream_loop -1 -i test.mp4 \
  -itsoffset 0.3 -i test.mp4 \    # 模拟300ms延迟
  -c:v copy -an \
  -f rtsp rtsp://localhost:8554/visible

# 模拟丢包环境（降低码率模拟网络恶化）
ffmpeg -re -stream_loop -1 -i test.mp4 \
  -c:v libx264 -b:v 1M -preset ultrafast \  # 降到1Mbps
  -an -f rtsp rtsp://localhost:8554/visible
```

## 5. 通信架构选型对比

### 5.1 核心问题：视频传输协议选 RTSP 还是 RTMP？

这是直接影响系统实时性的关键决策。

| 对比维度 | RTSP (over TCP) | RTSP (over UDP) | RTMP | Agora/WebRTC |
|----------|:---:|:---:|:---:|:---:|
| **端到端延迟** | 150-400ms | 100-300ms | 2-30秒 | 200-500ms |
| **画面可靠性** | ✅ TCP保证不丢帧 | ⚠️ 可能丢帧/花屏 | ✅ TCP保证 | ✅ 自适应 |
| **穿透防火墙** | ⚠️ 需要开放端口 | ⚠️ 需要开放端口 | ✅ 走80/1935 | ✅ 自动穿透 |
| **多客户端分发** | 需要额外中转 | 支持组播 | 需要流媒体服务器 | ✅ 原生支持 |
| **DJI Cloud API 支持** | ✅ 原生支持 | ✅ 原生支持 | ✅ 原生支持 | ✅ 原生支持 |
| **开源客户端库** | FFmpeg/GStreamer/Live555 | FFmpeg/GStreamer | FFmpeg/librtmp | WebRTC 库 |
| **部署复杂度** | 低 | 低 | 中（需流媒体服务器）| 高（需信令服务器）|

### 5.2 推荐方案：RTSP (TCP模式) 为主，RTSP (UDP模式) 为备

**理由**：
- RTSP 是 DJI Cloud API 支持的协议中延迟最低的
- TCP 模式保证画面完整不丢帧（排弹场景对画面可靠性要求高）
- 客户端实现简单（FFmpeg 一行代码拉流）
- 不需要额外的流媒体中转服务器

**降级策略**：当需要多客户端同时查看、或需要穿透复杂网络时，切换到 Agora WebRTC 模式。

### 5.3 遥测数据协议选型

| 选项 | 延迟 | 可靠性 | DJI 支持 |
|------|:---:|:---:|:---:|
| **MQTT** (QoS 1) | <100ms | 高 | ✅ Cloud API 原生 |
| HTTP 轮询 | 1-5s | 高 | 可自行实现 |
| WebSocket | <100ms | 高 | 可自行实现 |

**推荐**：MQTT QoS1——与 DJI Cloud API 原生兼容，零适配工作。

## 6. 分阶段实施方案

### 6.1 总体路线图

```
阶段0：仿真开发 (2个月)                      预算：¥0
  ├─ 搭建本地 RTSP + MQTT 仿真环境
  ├─ 开发视频接收/解码/渲染全管线
  ├─ 开发 AI 推理管线
  ├─ 集成到 Qt 指挥席客户端
  ├─ 用"坏的"视频素材做鲁棒性测试
  └─ 产出：可运行的仿真版指挥席

阶段1：链路验证 (1个月)                      预算：¥0 ~ ¥4,788
  ├─ 搭建真实 MQTT Broker + 流媒体服务器
  ├─ 部署 DJI Cloud API 后端 Demo
  ├─ (可选)买 DJI Mini 4 Pro 验证真实 RTMP/RTSP 推流
```

### 6.3 阶段1——何时需要买无人机、买什么

**阶段1的主要目标不是"飞"，而是"打通真实数据链路"。**

你需要验证的是：
1. DJI Cloud API 的 MQTT 消息格式是否和你的解析代码一致
2. DJI Cloud API 的 RTSP 流是否能用你的 FFmpegReceiver 正确解码
3. 端到端延迟到底是多少

这些验证只需要无人机通电+推流，不需要飞。最低成本的验证方案：

| 方案 | 硬件 | 成本 | 能力 |
|------|------|------|------|
| **最小方案** | 无——用 DJI Cloud API 公开 Demo | ¥0 | 只能搭好服务器端，无法验证真实视频流 |
| **推荐方案** | DJI Mini 4 Pro (RC-N2版) | ¥4,788 | 验证 DJI Fly 的 RTMP 推流格式，可见光管线 |
| **完整方案** | DJI Mavic 3T | ¥30,798 | 验证双光 RTSP + Cloud API MQTT，全能力覆盖 |

**判断标准**：如果你的团队对视频流处理完全没有经验，建议买 Mini 4 Pro 做链路摸底。如果团队有音视频开发经验，可以直接到阶段2再买 Mavic 3T。

## 8. 附录：术语解释

| 术语 | 通俗解释 |
|------|---------|
| **RTSP** | 一种视频流传输协议，类似于"直播视频的URL"。延迟低，适合实时监控。 |
| **RTMP** | 另一种视频流传输协议，最初为 Flash 设计。延迟较高（2-30秒），不适合实时场景。 |
| **H.264 / H.265** | 视频压缩编码标准。H.265 比 H.264 压缩效率高约50%。 |
| **I帧 / P帧** | I帧是完整画面（关键帧），P帧只记录和上一帧的差异。I帧丢了会导致花屏。 |
| **码率 (Bitrate)** | 每秒传输的数据量。1080p视频通常需要 4-8 Mbps。 |
| **MQTT** | 一种轻量级的消息传输协议，适合物联网设备上报数据。DJI 用这个协议推送飞行数据。 |
| **QoS (Quality of Service)** | MQTT 的消息质量保证级别。QoS0=可能丢，QoS1=至少一次，QoS2=恰好一次。 |
| **丢包率** | 网络传输中丢失的数据包比例。RTSP over TCP 理论上不丢包。 |
| **端到端延迟** | 从无人机拍摄到指挥屏幕显示的总时间。 |
| **O4 (OcuSync 4.0)** | 大疆第四代图传技术，无人机到遥控器的私有无线传输协议。 |
| **Cloud API** | 大疆提供的上云接口，让遥控器把视频和遥测数据推送到第三方服务器。 |
| **SRRC / FCC / CE** | 不同地区的无线电发射功率标准。中国用 SRRC，图传距离 10km。 |
| **MediaMTX** | 一个轻量级的 RTSP 流媒体服务器，用于仿真环境模拟视频源。 |
| **Mosquitto** | 一个轻量级的 MQTT Broker，用于转发遥测数据。 |
